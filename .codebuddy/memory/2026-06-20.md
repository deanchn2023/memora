## 修复：国内模型供应商配置保存后丢失

**问题**：配置国内模型（如 DeepSeek）测试成功 → 保存 → 重新打开设置 → 再次测试提示"尚未配置完成"，且对话栏供应商下拉框中看不到国内模型。

**根因**（两个 bug 叠加）：
1. `_loadProviderConfigs` 出于安全不回显密码字段（`input.value = ''`），但 `_saveProviderConfigs` 收集 DOM 值时把空字符串的 apiKey 发给主进程，`cc:set-config` 中 `'' !== undefined` 检查通过 → 用空字符串覆盖已保存的真实 API Key → `isProviderConfigured` 返回 false
2. `cc:get-config` 调用 `getAvailableProviders()` 只返回已配置的供应商，一旦密码被清空，该供应商从列表中消失，设置面板也无法正确加载

**修复**：
- `app.js _saveProviderConfigs`：password 字段为空时跳过（不发送），避免覆盖已保存的值；改为 `async` + `await`
- `app.js` 测试按钮和保存按钮调用 `_saveProviderConfigs()` 处加 `await`
- `main.js cc:get-config`：`getAvailableProviders()` 改为 `Object.values(PROVIDER_REGISTRY)`，返回所有供应商（含未配置的），设置面板需要显示全部供应商状态

**结论**：配置完成后，`getAvailableProviders()` 会正确返回已配置的供应商，对话栏供应商下拉框即可选到国内模型。

## 修复：腾讯云 ASR 签名错误 + SecretId 脱敏 + 语音按钮配色

**问题1：腾讯云 ASR 握手失败签名错误（两个根因）**
- 根因A：`asr-engine.js` `_generateSignature` 中签名原文路径缺少 appId
  - 错误：`asr.cloud.tencent.com/asr/v2?{params}`

- 根因B：签名被双重 URL 编码！`_generateSignature` 返回 `encodeURIComponent(signature)`，然后 `connect()` 中又对 params 做了一次 `encodeURIComponent(v)`，导致签名 `%` 被编码成 `%25`
- 修复：`_generateSignature` 返回原始 Base64 签名（不做 URL 编码），由 `connect()` 中的 `queryString` 统一做 `encodeURIComponent`

**问题2：SecretId/SecretKey 脱敏显示**

## 修复：腾讯云 ASR 签名错误（第三轮，彻底修复）

**根因**：签名 URL 构建方式与官方文档不一致
- 之前代码：URL 中所有参数（含签名）都做了 `encodeURIComponent`，且参数顺序为插入序（非字典序）
- 官方文档要求：非签名参数使用原始值（不 URL 编码）+ 按字典序排列，签名单独 `encodeURIComponent` 后追加到 URL 末尾

**修复（对照官方文档 https://cloud.tencent.com/document/product/1093/48982）**：
1. `asr-engine.js` `_generateSignature`：签名原文用原始值（不编码），返回原始 Base64
2. `asr-engine.js` `connect()`：URL 构建改为官方方式——排序后的原始 queryString + `&signature=encodeURIComponent(signature)`
3. 添加调试日志：输出签名原文、签名值、编码后签名、完整 URL（SecretId 掩码）、SecretId/SecretKey/AppId 前几位
4. `app.js` `_saveASRConfig`：所有输入值添加 `.trim()`，防止首尾空格导致签名错误
5. `main.js` `asr:start`：读取配置时添加 `.trim()`

## 修复：ASR 握手成功但未识别到语音内容

**根因**：`ScriptProcessorNode.onaudioprocess` 回调需要音频节点最终连接到 `audioContext.destination` 才能触发。之前为避免音频回授移除了 `processorNode.connect(destination)`，导致回调永远不触发，音频数据从未发送给 ASR。

**修复**：使用增益为 0 的 GainNode 作为中间节点：
```
sourceNode → processorNode → silentGain(gain=0) → audioContext.destination
```
- 音频数据流保持连通 → `onaudioprocess` 正常触发
- GainNode 增益为 0 → 扬声器无输出 → 无音频回授
- `stop()` 中同步清理 `silentGain` 节点

## 修复：语音按钮闪白屏退出（渲染进程崩溃）

**根因**：三个层面的问题导致渲染进程崩溃：
1. **macOS 麦克风权限未检查** — dev 模式下 `getUserMedia` 如 macOS 系统级权限未授权，可能导致 GPU 进程崩溃，进而导致渲染进程崩溃（白屏+reload）
2. **`onaudioprocess` 回调无 try/catch** — 音频处理中的异常未捕获，直接导致渲染进程崩溃
3. **IPC `asrAudioChunk` 返回的 Promise 未 `.catch()`** — 高频 IPC 调用（每 ~85ms 一次）中未捕获的 Promise 拒绝会累积导致崩溃

**修复**：
1. `main.js`：导入 `systemPreferences`，新增 `asr:check-mic-permission` IPC 处理器，使用 `getMediaAccessStatus('microphone')` 检查权限，`askForMediaAccess('microphone')` 请求权限
2. `preload.js`：新增 `asrCheckMicPermission` API
3. `app.js` `_startVoiceInput`：启动前检查 macOS 麦克风权限，未授权时提示用户去系统设置
4. `app.js` `_testASRMicrophone`：测试前也检查权限
5. `app.js` `onChunk` 回调：添加 try/catch + `.catch()` 防止未捕获 Promise
6. `voice-recorder.js` `onaudioprocess`：整体包裹 try/catch，防止异常导致渲染进程崩溃

## 修复：SIGSEGV 最终定位与解决（第六轮）

**精确崩溃点（同步日志定位）**：
```
Step 3 OK: state=recording   ← MediaRecorder.start(500) 成功
crashed 11                   ← ondataavailable 回调中 decodeAudioData() 触发崩溃
```
`AudioContext.decodeAudioData()` 即使在 suspend 状态下调用也会激活音频解码管道，触发 macOS SIGSEGV。

**最终解决方案**：
1. `voice-recorder.js`：彻底去掉所有 `AudioContext`/`decodeAudioData`，只用 `MediaRecorder` 采集 WebM/Opus 数据，音量用数据包大小估算
2. `main.js`：新增 `ffmpeg` 管道（`_startFfmpegPipe`/`_stopFfmpegPipe`），主进程收到 WebM chunk 后写入 ffmpeg stdin，ffmpeg 输出 16kHz PCM（s16le），分成 6400 字节小包发给 ASR
3. ffmpeg 路径：`/opt/homebrew/bin/ffmpeg`（macOS Homebrew）或 `$FFMPEG_PATH` 环境变量

**架构**：渲染进程 MediaRecorder → IPC → 主进程 ffmpeg stdin → ffmpeg stdout PCM → ASR WebSocket

## 修复：4007 音频解码失败（第五轮）

**根因**：腾讯云 ASR `voice_format` 枚举：1=PCM, 4=speex, 8=mp3, 10=opus裸流(特殊封装), 12=WAV, 16=AAC。**不支持 WebM 容器**。MediaRecorder 默认输出 webm/opus，不能直接发。

**修复**：
- `voice-recorder.js`：用 `AudioContext.decodeAudioData()` 解码每个 WebM chunk → Float32 PCM → `_toPCM16` 重采样到 16kHz 16-bit → 发给 ASR
- `asr-engine.js`：`voiceFormat = 1`（PCM），因为 VoiceRecorder 在前端完成解码转换
- `AudioContext` 仅用于 `decodeAudioData`（调用后立即 `suspend()`），不连接任何输出节点，不会触发 SIGSEGV
- 每 500ms 一个 chunk（比 250ms 更完整的 WebM header，decode 更稳定）

## 修复：测试麦克风闪白屏（第二轮修复）

**根因**：`voice-recorder.js` `start()` 方法中 `processorNode.connect(this.audioContext.destination)` 将麦克风音频直接输出到扬声器，造成音频反馈回路，可能导致渲染进程崩溃
- 同时缺少 `navigator.mediaDevices` 可用性检查，在不支持的环境下直接调用 `getUserMedia` 会抛出未捕获异常

**修复**：
1. `voice-recorder.js start()`：移除 `processorNode.connect(audioContext.destination)` 连接，只保留 `sourceNode.connect(processorNode)`，避免音频回授
2. `voice-recorder.js start()`：添加 `navigator.mediaDevices` 可用性检查，不可用时抛出友好错误
3. `app.js` 顶部添加 `window.addEventListener('error', ...)` 和 `window.addEventListener('unhandledrejection', ...)` 全局错误捕获，`e.preventDefault()` 阻止错误导致页面崩溃

## 全面性能优化（v3.0 分支）

**分支**：`v3.0`（从 `v2.1-multimodal` 创建）

### 渐进变慢根因（内存泄漏类）
1. **MutationObserver 无节流**：流式 AI 输出时每个 text.delta 触发 MutationObserver → `_updateScrollButtons()` → 3次 DOM 查询，高频触发导致性能急剧下降
2. **`_saveCurrentSessionMessages` 无防抖**：每次 AI 消息完成+视图切换+会话切换都会调用 `querySelectorAll('.message').forEach(msg => msg.outerHTML)` 序列化整个聊天 DOM，长对话时非常慢
3. **定时器内重复 DOM 查询**：ADP/CC 流式定时器每秒 `querySelector('#adpProgressTimer')` 查询元素
4. **main.js before-quit 未清理 configPolling/notificationPolling**：退出时残留网络请求

### 渲染卡顿根因
1. **72 处 `backdrop-filter`**：blur(20px)+saturate(180%) 在滚动容器上 GPU 合成开销极大
2. **221 处 `transition: all`**：每帧检查所有 CSS 属性变化
3. **流式输出时动画不暂停**：每个 text.delta 更新 DOM 触发重绘+过渡动画

- **MutationObserver + scroll**：`requestAnimationFrame` 节流，缓存 DOM 引用
- **`_saveCurrentSessionMessages`**：500ms 防抖，beforeunload 时同步保存
- **定时器**：缓存 timer DOM 元素，不再每秒查询
- **CSS `performance.css`**：`content-visibility: auto` 懒渲染离屏消息/列表；聊天区域强制关闭 `backdrop-filter`；`contain: layout style paint` 隔离重绘
- **`body.streaming-active`**：流式输出时全局禁用 transition/animation
- **main.js**：before-quit 补充 `stopConfigPolling()` + `stopNotificationPolling()`

- 431 处 `addEventListener` vs 5 处 `removeEventListener`（需重构为事件委托）
