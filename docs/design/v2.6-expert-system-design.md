# Memora v2.6 专家系统设计方案

> 版本：v2.6.0 | 日期：2026-06-14 | 状态：已确认，待开发

---

## 一、需求概述

将 AI 助手页面当前的 3 个硬编码功能卡片 + 硬编码快捷问题，改造为**可配置的专家/专家团卡片**系统：

1. **专家（Expert）**：映射一个 ADP Agent，包含访问地址、AppKey、名称、介绍、快捷访问
2. **专家团（Expert Group）**：选择多个专家组合，指定一人为主持人，实现群聊模式
3. 点击**专家卡片** → 直接与该 Agent 对话（现有 ADP 流程不变）
4. 点击**专家团卡片** → 群聊模式，主持人先发言再分发任务
5. **专家及专家团配置仅登录用户可用**（复用现有 `isLoggedIn` 机制）

### 2.2 专家团配置（ExpertGroup）

```js

```

### 2.3 存储位置

- **主进程持久化**：`userData/experts.json`，通过 `electronAPI` 读写（与现有 Store 模式一致）
- **结构**：
```json
{
  "experts": [ /* Expert[] */ ],
  "groups": [ /* ExpertGroup[] */ ],
  "version": "2.6.0"
}
```
- **权限控制**：只有 `isLoggedIn === true` 时才可读写专家/专家团配置；未登录时卡片区域只展示默认欢迎信息
- **远程同步**：通过 Config Server v3 同步 API 同步（后续版本）

## 五、专家对话流程（单专家模式）

与现有 ADP 对话完全一致，只是 `appKey` 和 `adpUrl` 从专家配置读取而非全局配置：

```
用户点击专家卡片
  → 设置 _activeExpertId = expert.id
  → 切换快捷访问为该专家的 quickAccesses
  → 用户发送消息
  → sendADPMessage({ appKey: expert.appKey, url: expert.adpUrl, ... })
  → SSE 流式响应（现有流程不变）
```

**无需改动**：`_handleADPSSEEvent`、`_finishADPMessage` 等全部复用。

## 六、专家团群聊流程（核心设计）

### 6.1 交互流程

```
用户点击专家团卡片
  → 进入群聊模式
  → 界面顶部显示：🏆 招投标梦之队（3位专家）
  → 费用提醒弹窗："此群聊将调用 N 位专家，预计消耗 N+2 次 AI 调用，是否继续？"
  → 用户确认后，主持人（host）先发言
```

### 6.2 群聊 UI — 时间线平铺模式

所有专家消息按**发言时间顺序**平铺在同一个聊天区域，类似真实群聊体验：

**UI 要点**：
- 每条消息上方有**专家标签栏**（头像 + 名称 + 角色标记）

- 消息按**发言时间顺序**排列
- 进度指示器显示当前正在调用的专家
- 正在调用的专家消息区域显示 loading 态

### 6.3 群聊对话引擎（核心算法）

#### 阶段一：主持人首轮发言

```
用户发送消息 →
  1. 构建主持人 Prompt：
     -- 自定义 Prompt 前缀（如果 hostPrompt 非空，使用用户自定义 Prompt）--
     {hostPrompt 或默认模板}
     
     "你是专家团「{groupName}」的主持人。
      团队成员：{experts简介列表}
      
      用户的请求是：{userMessage}
      
      请你：
      1. 分析用户请求
      2. 判断需要哪些专家参与
      3. 为每个需要的专家分配具体任务
      4. 以你的专业角度先给出初步判断
      
      输出格式（必须严格遵循）：
      {
        "analysis": "你的分析",
        "initial_thought": "你的初步判断",
        "assignments": [
          {"expert_id": "expert_002", "task": "具体任务描述"},
          {"expert_id": "expert_003", "task": "具体任务描述"}
        ]
      }"
  
  2. 调用主持人 ADP（host.appKey）
  3. 解析主持人输出中的 assignments
  4. 显示主持人消息到聊天区
```

**主持人自定义 Prompt 机制**：

- 如果 `group.hostPrompt` 非空，将其作为主持人系统 Prompt 的**前缀**
- 默认模板追加在自定义 Prompt 之后，保证输出格式约束不丢失
- 自定义 Prompt 示例：
```
你是一位资深招投标专家，擅长技术方案评审和项目风险评估。
在分配任务时，优先考虑方案的可行性和风险控制。
对于技术类问题，优先交给技术专家处理；对于商务类问题，优先交给商务专家。
```

#### 阶段二：分发任务给专家（串行 + 并行双模式）

**串行模式（v2.6 默认）**：
```
  5. 按顺序调用 assignments 中的专家：
     每个专家的 Prompt：
     "你是专家「{expert.name}」。
      专家团主持人「{host.name}」分配给你的任务是：
      {assignment.task}
      
      用户的原始请求：{userMessage}
      
      请完成你的任务。"
  
  6. 每个专家响应完成后，显示其消息
  7. 如果专家回复中明确指向另一位专家：
     检测规则：回复中包含 @专家名 或 "请{专家名}处理"
     → 自动将该结果转发给对应专家
     
  8. 否则，将专家结果汇总给主持人
```

**并行模式（v2.6 可选，后续增强）**：
```
  5. 同时调用 assignments 中的所有专家
  6. 使用 Promise.allSettled() 收集所有结果
  7. 按完成顺序依次显示消息
  8. 失败的专家跳过，在主持人总结中说明
```

**执行策略配置**：
```js
// ExpertGroup 新增字段
{
  executionStrategy: 'serial',  // 'serial' | 'parallel'
}
```

#### 阶段三：主持人总结

```
  9. 汇总所有专家结果，调用主持人：
     "以下是各专家的工作结果：
      {expert1.name}: {expert1.result}
      {expert2.name}: {expert2.result}
      
      请你：
      1. 综合各专家结果
      2. 检查是否有遗漏或冲突
      3. 如需补充，指定哪些专家需要补充
      4. 给出最终结论"
  
  10. 主持人输出最终总结
  11. 如果主持人要求补充 → 回到阶段二（限制最多2轮补充，避免死循环）
```

#### 错误处理：跳过继续

```
  专家调用失败时：
  1. 在聊天区显示错误标记：
     "┌─ 📊 数据分析专家 ❌ ──────────────────────────┐
     │  ⚠️ 调用失败：{error message}                  │
     └─────────────────────────────────────────────────┘"
  2. 跳过该专家，继续执行后续专家
  3. 在主持人总结中说明：
     "注意：数据分析专家调用失败，以下结论缺少该专家的输入"
```

### 6.4 费用提醒机制

用户发送群聊消息前，弹窗提醒：

```
┌────────────────────────────────────────────────┐
│  ⚠️ 费用提醒                                   │
├────────────────────────────────────────────────┤
│                                                 │
│  此群聊将调用 {N} 位专家：                       │
│                                                 │
│  1 次主持人分析 + {N-1} 次专家调用 + 1 次汇总    │
│  = 共 {N+1} 次 AI 调用                          │
│                                                 │
│  如需补充轮次，可能额外增加调用次数。              │
│                                                 │
│           [取消]  [继续，我了解了]                │
│                                                 │
│  ☐ 不再提醒（本会话）                            │
└────────────────────────────────────────────────┘
```

- 首次群聊消息必弹
- 勾选"不再提醒"后本会话内不再弹出
- 每次新建群聊会话重置提醒状态

### 6.5 多轮对话上下文

```
第二轮用户消息 →
  1. 从上一轮结果中提取所有专家的输出
  2. 构建上下文发送给主持人：
     "上一轮对话结果：
      你（主持人）: {host_previous_output}
      {expert1.name}: {expert1_previous_output}
      {expert2.name}: {expert2_previous_output}
      
      用户的新消息：{newUserMessage}
      
      请继续作为主持人响应。"
  3. 重复阶段一至三
```

### 6.6 执行策略

| 策略 | 说明 | 适用场景 | v2.6 支持 |
|------|------|----------|-----------|
| **串行** | 主持人 → 专家1 → 专家2 → ... → 主持人总结 | 默认，便于控制上下文和顺序 | ✅ |
| **并行** | 主持人 → 同时调用所有专家 → 主持人总结 | 专家间无依赖时更快，但结果不可交叉引用 | 🔜 v2.7 |

### 6.7 会话管理

- 专家团群聊的 `conversationId` 使用 `{sessionId}_{groupId}` 格式
- 每个专家的 `conversationId` 独立，不跨专家复用
- 聊天记录保存时，每条消息附带 `expertId` 和 `role`（host/member）
- 恢复会话时，根据 `expertId` 渲染不同的专家头像和名称

新增 IPC 通道：

| 通道 | 方向 | 说明 |

**权限校验**：所有 IPC 通道在 main 进程检查 `isLoggedIn`，未登录返回空数据或错误。

### 7.2 sendADPMessage 扩展

现有 `sendADPMessage` 只使用全局配置的 `appKey` 和 `url`。改造为：

```js
// 单专家模式
sendADPMessage({
  message, conversationId,
  appKey: expert.appKey,        // 从专家配置读取
  url: expert.adpUrl || null,   // 留空用全局默认
})

// 专家团模式 - 主持人
sendADPMessage({
  message: hostPrompt,
  conversationId: hostConversationId,
  appKey: host.appKey,
  url: host.adpUrl || null,
  systemRole: group.hostPrompt || '你是专家团主持人...'  // 自定义或默认
})

// 专家团模式 - 成员专家
sendADPMessage({
  message: memberPrompt,
  conversationId: memberConversationId,
  appKey: member.appKey,
  url: member.adpUrl || null,
  systemRole: `你是专家「${member.name}」。`
})
```

### 7.3 群聊消息渲染
